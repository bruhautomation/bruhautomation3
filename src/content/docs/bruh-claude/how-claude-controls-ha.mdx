<Detail max={1}>

Claude gets three kinds of access to your home, each with its own job:

- **Terminal commands** — for working on your configuration files: editing YAML, checking logs, making backups.
- **A live connection** — for reading and controlling the home right now: lights, sensors, cameras, history. This is the *only* path Claude's actions take, so safety limits set here cover everything.
- **Admin services** — for reorganizing: renaming things, creating rooms and labels, building dashboards. These are real Home Assistant services, so your own automations can use them too.

You never pick a layer — you just ask, and Claude routes the request. The full architecture, including why the layers aren't redundant, is further up the **Detail** slider.

</Detail>

<Detail min={2}>

BRUH Terminal gives Claude three ways to touch Home Assistant, and at first glance they look like three overlapping control panels. They're not — they're **one brain with one set of hands, plus a toolbox anyone in the house can reach**. This page explains what each layer is for, how they interact, and exactly where the (small, deliberate) overlap is.

## The three layers in one table

| | **CLI tools** (`ha-*`) | **MCP tools** | **Power Tools** (`bruh_claude.*` services) |
|---|---|---|---|
| **What it is** | Shell commands in the terminal | Claude's live API into HA | Real HA services registered by the integration |
| **Who can call it** | You and Claude, in the terminal only | Claude only (terminal, voice, tasks) | **Anyone**: Claude, automations, scripts, Developer Tools, voice |
| **What it touches** | Files & workflow: YAML, logs, backups, memory, packages | Live state: entities, devices, cameras, history, registries, dashboards | Admin state: areas, labels, helpers, users, dashboards, zones… |
| **Example** | `ha-reload automations` | `get_camera_snapshot`, `control_light` | `bruh_claude.create_helper` |

## How they fit together

**MCP is Claude's only pair of hands.** Everything Claude does to your live home — reading a sensor, turning on a light, looking at a camera, calling *any* service — goes through the MCP server's 36 tools. That single funnel is what makes safety enforceable: per-agent service deny-lists and voice tool-scoping are applied at that chokepoint, once, and cover everything.

**Power Tools are not a second pair of hands — they're verbs installed into HA itself.** Registering the 56 admin operations as real `bruh_claude.*` services (instead of private Claude abilities) is a deliberate choice with three payoffs:

1. **Claude reaches them through MCP** like any other service (`call_service` → `bruh_claude.create_area`), so the same deny-lists and budgets apply.
2. **Your automations and scripts get the same superpowers** with no Claude in the loop — a nightly automation can call `find_orphaned_references` by itself.
3. **You can drive them by hand** from Developer Tools → Actions, with field pickers and validation.

**CLI tools are the workshop bench**, and they only exist inside the terminal. They cover the file-and-workflow side that live APIs don't: editing and reloading YAML, tailing logs, git backups, the memory store, persistent packages. Claude uses them for config work; you use them when you're in the shell anyway.

So the flow for any request is:

```text
"Label everything battery-powered and build me a guest-mode toggle"
        │
        ▼
   Claude (terminal / voice / task)
        │  MCP — the single funnel (deny-lists enforced here)
        ├── get_registry ─────────── read: which entities, which labels exist
        ├── call_service ──────────► bruh_claude.add_label        (Power Tool)
        └── call_service ──────────► bruh_claude.create_helper    (Power Tool)

"Fix my automations.yaml indentation and reload"
        │
        ▼
   Claude (terminal)
        ├── edits the file directly (terminal file access)
        └── ha-reload automations                                  (CLI tool)
```

## Is there redundancy?

A little, and it's intentional — same verb, different caller:

| Looks duplicated | Actually |
|---|---|
| `ha-service call` (CLI) vs `call_service` (MCP) | Same HA endpoint. CLI version exists so *you* can call services from the shell; Claude always uses MCP (that's where deny-lists live). |
| `ha-entity get` (CLI) vs `get_entity_state` (MCP) | Same read. One for humans at a prompt, one for Claude. |
| `get_areas` (MCP) vs `get_registry areas` (MCP) | `get_areas` is the voice-optimized room→entities map; `get_registry` is the admin view with ids. Different questions. |

Nothing here is a dead layer to remove. Collapsing to "just one layer" would mean either taking services away from your automations (making them Claude-only), or pushing file/YAML work through an API that can't do it.

</Detail>

<Detail min={2}>

The rule of thumb:

> **Files → CLI. Live home → MCP. Admin changes → Power Tools (via MCP).**

Claude's generated context teaches it this routing, so you never have to think about it — you just ask.

</Detail>

## What Claude can and can't reach

The goal is an instance where Claude can do essentially everything — here's the honest scorecard:

**Fully covered:** entity/device control for every major domain; cameras; history and statistics; automations, scripts, and scenes (YAML + reload); areas, floors, labels; entity naming, ids, aliases, icons, visibility; helpers (all 8 types); zones; persons; users; dashboards including custom-card resources; blueprints; statistics backfill; integration enable/disable/reload; repairs; logs, traces, templates; config backup and restore.

**Deliberately excluded:**
- **Adding or removing integrations** — config flows are interactive (OAuth, discovery, pairing buttons). Claude walks you to the right screen; you click.
- **Credentials and auth internals** — API keys inside `core.config_entries`, tokens, MFA. Never read, never written, never backed up to git.
- **YAML-mode dashboards/helpers/persons** via services — those belong to your configuration files, which Claude edits directly in the terminal instead.
- **HA Core/OS updates and add-on installs** — Supervisor territory; `ha-addon` covers restarts and logs, but installs stay a human decision.
