<Release version="1.46.0" date="September 5, 2026" latest>

**The last three things on the list, and the mechanism two of them needed.** brAIn's capability map ranked twelve changes by how much of a house each one would change; this release finishes the twelve. One-off intents were **#1** on it and had been unbuildable until the shadow runner existed; the scene designer was the half of **#11** the thermal model left; and the condition an over-ridden automation is missing is what **#9** named and deferred when the override ledger shipped. All three are new producers on the [Proposals](/brain/proposals/) tab, and two of them have to *edit* somebody's YAML rather than append to it — which is the new mechanism, and the part that had to be right first.

<Changes type="added">

- **Changing one entry without touching a byte of the rest of the file.** 1.44.0's writer appends and never re-serialises, because `automations.yaml` is your file with your ordering, your comments and your quoting in it — and two of this release's producers have to change an entry that is already in it. Re-serialising the list to do that would hand back a diff nobody asked for on every press, so an edit is a **byte splice** instead: the YAML is composed into a node tree without constructing any of it, and every node carries offsets into the very text that was parsed. The load-bearing test is therefore not *"the file still parses"* — a round trip through the YAML library would pass that, keep every value and quietly delete every comment — but that **every byte outside the entry is identical** before and after.
- **Three things make that span honest, and each of them is a refusal.** A block collection's end runs on to whatever token ended it, so the last entry in a file would swallow the comment after it and one followed by a blank line would swallow that; the leading `- ` is not part of the node and has to be walked back to, across a newline, because an item written with its keys on the next line is the same item. And anything that cannot be cut on a line boundary — two entries under one id, a document that is not a top-level list, an item sharing its last line — is refused rather than approximated. Nearly-right bytes are your file with a hole in it.
- **[The condition an automation you keep undoing does not have](/brain/proposals/#the-condition-it-is-missing).** The override finding already reports the fight — *"you have put Evening lights back 11 times, on 8 separate weekday evenings"* — and then leaves you to open the automation editor and work out what to write. This is the change that answers it, with the ledger's own numbers on the card and the automation spliced in place rather than added beside.
- **One condition, and it is negated.** The obvious shape is wrong in the direction that breaks a working house: a `time` condition is a **conjunction**, so an automation carrying one stands down every Saturday and Sunday as well, at every hour. What the evidence supports is far narrower, so what gets written is one `time` inside a `not`. The band comes from the override ledger and is **never re-derived** — every floor that makes a band mean something already lives there, and a second answer to *"is this a pattern"* is the one nobody can see.
- **The case on the card is a pair of numbers**, because one alone is a fact about an automation rather than an argument for changing it: *"it ran 30 times; with this condition it would have run 22 — 8 fewer, in the hours you keep putting it back."* If the two come out the same the card says so rather than dressing it up.
- **Four refusals, and none of them is a card.** An automation with no `id` (Home Assistant's own editor cannot change one either, so the reason names that rather than pretending brAIn is what is in the way), one that already stands down over those hours, one whose existing time condition names an entity instead of a clock — *"I could not tell"* may not be read as *"there is nothing there"* — and a protected target. Each is reported in **⚙ Diagnostics** with the automation it is about, because every card on the Proposals tab is something you can answer and these are not.
- **[A sentence that happens once](/brain/intents/).** *"Turn the porch light off when the guests leave."* Type it into the ask bar — anything opening *when…*, *once…*, *the next time…*, *tell me when…* — or call the new **`brain.intent`** service, which is how a voice command reaches it. What gets written is an ordinary automation with `mode: single` and one extra action nobody asked the model for: `automation.turn_off` on itself. Home Assistant does the running, there is no listener in the add-on to keep alive across a restart, and nothing is left *doing* anything afterwards.
- **Nothing removes it on its own.** What is left is a card saying it fired, with a **Remove** on it — because an automation that vanished from your file while you were not looking is a file you cannot trust. One that has waited a fortnight without firing is *labelled*, not deleted: that almost always means the thing already happened and nobody told the house, and the answer to it is a sentence with a button on it. brAIn learns that it fired from the automation's own `last_triggered`, stamped after the accept, rather than from it being switched off — you switching it off by hand is not it having fired.
- **Claude writes the config once, with reading tools only, and everything it returns is checked.** The trigger has to be **replayable**, not because a one-off needs a shadow week but because the replay is the only sanity check there is on a trigger that has never fired. It has to act **once**, and a standing rule is a refusal **with the restatement shown** — *"every evening at sunset"* is a good thing to want and belongs on the path that gives it a trial. It has to name something. And it may not touch a protected entity. A refusal is a **row on the tab** rather than a log line: somebody typed a sentence and is waiting for an answer.
- **[Four moods for a room](/brain/scenes/).** *"Design my evening for the living room"*, or a room picker at the top of the Proposals tab. Morning, day, evening and night, composed from the registries: a colour temperature where the bulb takes one, a colour where it cannot, brightness where there is neither, on and off where there is not even that — and a bulb whose modes cannot be read gets the last of those rather than being dropped. Night is the only mood that turns most of the room off, and which light stays on is matched on its name, because there is no attribute for *"this is the one I leave on"*.
- **The evidence is the picture, because there is no replay and no week.** A swatch per light per mood, an off light drawn as an empty outline rather than a dark square, the bulbs named in text under the strip because a phone has no hover, and a protected light shown as **skipped**. Accepting writes them to `scenes.yaml` through the same snapshot-append-reload-verify-revert path, waiting for all four scenes to appear rather than the first. Claude is used for exactly one thing and it is the naming; a failed run leaves *Morning*, *Day*, *Evening* and *Night*, which work fine.
- **The schedule is offered only once the four scenes really exist**, and read off `scenes.yaml` rather than off the proposals store — somebody who copied the card's YAML in by hand has earned it exactly as much as somebody who pressed the button. It is an ordinary automation, so unlike the scenes it can be tried for a week. Morning and night use the times brAIn has **measured** for when this house gets up and settles; midday and the early evening are not things a wake-time measurement can see, so they are fixed guesses and the card says which two.

</Changes>
<Changes type="fixed">

- **The replay skipped everything inside a `choose`.** It walked past one along with the delays and the waits, so the check that reads what an automation would *do* — the one the protected-entity refusal stands on — saw nothing at all in a `choose` and passed it vacuously. It walks `choose`, `if`/`then`/`else`, `repeat`, `parallel` and `sequence` now, to a bounded depth.
- **A `time` condition that wrapped midnight was replayed backwards.** Home Assistant reads `after` later than `before` as *"from tonight until tomorrow morning"*, and 22:00–01:00 is the commonest window anybody writes one for. Testing the two bounds separately answers *no* at every instant of such a window — so a `not`-wrapped one passed at every instant instead, which is exactly the shape this release's condition proposal writes.
- **A YAML file holding nothing but a comment was read as unreadable** and refused. Home Assistant's own loader answers the same thing to an empty document and a broken one, so the distinction is drawn in the writer — and a `scenes.yaml` with one header line in it is the ordinary case on a house that has never saved a scene.

</Changes>
</Release>

<Release version="1.45.0" date="September 4, 2026">

**The house acts.** Everything brAIn had ever done to a house was a person's press on a specific card. These are the first two things that are not, and both are deliberately the narrowest shape that still does the job — every line of each is about what it will not do. It also carries the change the chat needed to work the way a terminal does: several conversations answering at once, and a switch between them that stops nothing.

<Changes type="added">

- **[Overnight self-healing](/brain/self-healing/) — three things brAIn may fix while you are asleep, and it ships off.** Start an add-on that was set to run at boot and is not running, ping a Z-Wave node the controller has marked dead, reload a config entry that failed to set up. All three are calls you would have pressed yourself and all three fail into nothing. **No power-cycling of anything**, no restart of Home Assistant, no restart of brAIn, and **no Claude run anywhere on that path** — a model choosing what to restart at 3am is a guess wearing a repair.
- **It runs once a night, inside a window you already set.** Quiet hours if you have them; an hour after the settle time brAIn has *measured* if you have not; **with neither it does not run at all**, and ⚙ Diagnostics says so in as many words — a self-healer that has never run looks exactly like one that had nothing to do, and running at an hour nobody set is acting on a guess about when nobody is looking. A night is keyed around local midnight, so 23:40 and 03:10 are the same night rather than two passes twenty minutes apart.
- **Five more refusals, each tested against the mutation that removes it.** At most three repairs a night, oldest first, so a night that hits the cap takes the same three every time. One attempt per **finding** per night, written to disk after every attempt rather than at the end, so a restart at three in the morning does not start the same add-on twice. Only `open` findings — one you answered is a conversation you are already having. Never a protected entity, area or device, asked with the same patterns the automation writer uses, and a target that cannot be resolved to plain entities is **skipped rather than guessed**: a ping reaches the box, so every entity on that node's device is checked. And never off a snapshot key that could not be fetched, because *I could not look* is not *it went away*.
- **Verification is the next checks pass, and the morning tells you.** Nothing reads back whether the call worked: a `200` from the Supervisor is a request being accepted, not an add-on that is running. What proves a heal is the finding clearing — *"started the Mosquitto broker add-on at 03:10; it is working now"* / *"…it has not cleared yet"* — and something mended overnight is itself a reason to send that morning's brief.
- **`sys.entry_failed`**, the check the third remedy stands on. An integration that fails setup takes everything it provides out of the house at once, so there is no state left to look wrong and nothing else on the Findings tab can see it. The entry list goes **unavailable rather than empty** when Core will not answer, and a **disabled** or **ignored** entry is somebody's decision rather than a fault.
- **[Emergency playbooks](/brain/playbooks/) — the automation you would want on a bad night, offered as a proposal.** Smoke or CO, a water leak, and a freeze with the heating stopped. **brAIn never runs one**: it writes it, offers it on the Proposals tab, and Home Assistant runs it if — and only if — you accepted it, through 1.44.0's write-reload-verify path with every refusal that already carries.
- **Nothing unlocks anything, ever.** `lock` and `alarm_control_panel` are refused across every playbook, and the rule is asserted over the **finished config** rather than over the branch that would have written one. A lock is the canonical protected entity, a smoke detector is the sensor most likely in a house to fire on burnt toast, and opening the house on a false alarm at three in the morning is the worst outcome any of this could produce.
- **Composed deterministically from your registries.** No model picks which valve closes — that is a guess wearing a config, and one nobody can check afterwards because the automation looks the same either way. Claude writes exactly one optional thing, the paragraph on the card, and a run that fails leaves the deterministic sentence in place.
- **Every entity it would act on is on the card by name**, grouped by what happens to it, with anything protected rendered as *skipped: protected* rather than silently dropped. A playbook with nothing left to do after protection is **not proposed** — what remains is a notification, and brAIn already sends those. `freeze` is the exception and says so, because nothing here may turn a boiler on.
- **A switch is a water shutoff when the word is the whole word** — `water`, `valve`, `stopcock`, `mains`, `shutoff`, and deliberately **not** a bare `main`, which `switch.main_bedroom_lamp` matches. A shutoff called only "Main" is missed, which costs a line on a card you can read; the other way round costs trust.
- **Rehearse it** renders every call the playbook would make with each target's state right now — *"12 lights → on (3 already on), 1 valve → closed (open now)"* — and **executes nothing**. It deliberately does not use `automation.trigger`, which would run the actions: that is not a rehearsal, it is the emergency. A real rehearsal is setting the detector off on purpose and reading the trace, and the card says so.
- **No trial button on a playbook**, and the reason where the button would have been: a trial replays the week you lived through, and that week had no emergency in it. The declined key follows the **sensor set**, so fitting another detector re-offers and rewording the card does not.

</Changes>
<Changes type="changed">

- **[The chat keeps every open conversation alive](/brain/terminal/#several-conversations-and-switching-stops-nothing), and switching between them stops nothing.** *"I'm trying to switch conversations and it keeps giving me a 409 that Claude is still responding. I thought the whole point was like a hot swap between these conversations."* That was right, and the refusal was honest rather than lazy: the chat held **one** Claude Code process, so switching was a stop and a `--resume`, and refusing mid-answer was the only alternative to throwing an answer away. The fix isn't a better refusal — it is to stop having one process. Every open conversation now holds its own, the way a terminal tab does. Leave one mid-answer and it carries on writing into its own transcript; it is finished and waiting when you come back.
- **Every row says what its own session is doing.** Three states and only two of them draw anything: nothing at all for the ordinary case, a quiet **answering…** while a reply is being written in the background, and **Needs your OK** for one waiting on a permission card. The marks are on both surfaces — the rail and **⋯ → Conversations** — joined server-side once, so the two can't disagree about whether a row is answering, and pushed down the stream rather than polled, because the answer only changes when something already had an event to send.
- **A background approval reaches you.** The card behind **Needs your OK** declines itself after ten minutes, so a badge on a list is half an answer — and a phone has no rail at all. The chat you *are* in raises a toast naming the conversation, with a button that opens it.
- **The cap is on processes, not on conversations** — **⚙ Settings → Conversations kept open at once**, three by default, one to eight (`chat_max_sessions`). You may have as many conversations as you like and Claude Code keeps every one; one with no process is a transcript and an id. Past the cap, the session untouched for longest is closed — **never one that is mid-answer**, because an answer surviving you looking elsewhere is the whole point, and an eviction that could take the busy one would break exactly the thing it exists to protect. The closed one keeps its transcript, keeps its row, and gets a note saying why, so going back explains the gap rather than reading as a crash; the next message there picks the conversation straight up again.
- **One 409 is left and it is about the cap**: every open chat still answering with nothing idle to close. It names the count and the setting rather than blaming an answer you can still watch being written. Picking a **model** is still refused mid-answer — the model is a flag on the process and applying it is a restart that would lose the reply — but the sentence now says which conversation is busy and offers what works, which is to go and talk in another one.
- **One transcript file per conversation** (`/data/chat/`). A single file was the shape of a single session, and two live ones writing it would each hold half a scrollback; the old file is read across once on upgrade, so nothing anybody was part-way through is blanked. **Deleting a conversation any session is holding is refused** — not only the one on screen — and the ✕ offers to close that session first rather than leaving a no, asking as it goes, because closing one mid-answer loses what it was writing.

</Changes>
</Release>

<Release version="1.44.0" date="September 4, 2026">

**The two steps that make a proposal mean anything.** 1.42.0 shipped the Proposals lifecycle — `proposed → trialling → accepted | declined` — and the last two did nothing: *Try it for a week* set a status and an end date, and nothing ever looked at the week; **Accept recorded a status and never created the automation**. A feature that does nothing is indistinguishable from one that is broken, and from the tab both of these read as the second.

<Changes type="added">

- **A trial is a replay of the week you lived through, graded against what you actually did.** Nothing subscribes to live events and nothing needs to: the recorder already holds when the proposed automation would have fired, and brAIn's own ledger of person-caused changes already holds what you did at those moments — so a trial is arithmetic over two things that exist. It is re-run on **every checks pass** rather than once at the end, because a replay costs one history fetch and *"three days in: it would have fired three times and you did the same twice"* is worth more than a card that says nothing until Sunday. Three verdicts, and the third is the one worth having: **agreed** (you did the same thing within a quarter of an hour), **nothing happened** (weak evidence either way, and named for it rather than counted against the change), and **you did the opposite** — you would have undone it, which folding into "nothing happened" would report as merely unproven. Each firing lands in exactly one bucket, decided by the nearest press, so a verdict cannot depend on the order the ledger is in. A refusal is carried rather than zeroed: *"it would never have fired"* and *"brAIn cannot replay this"* are different answers, and so is an action that is not one entity going to one state. When the week is up the row stays where it is with its report attached — ending a trial is your press.
- **A yes becomes a real automation, and it can be taken back.** Accept appends one entry to `automations.yaml` with an `id` of `brain_<proposal id>`, the title as its alias and a description saying where it came from. Your file is not reformatted — everything above the new entry is byte-for-byte what you wrote, comments and all — and it is snapshotted into the same edit journal Claude's own edits go into **before** it is touched, so `brain undo` reverts this exactly as it reverts anything else.
- **Written, reloaded, and *verified* — three claims that were being reported as one.** *The file was written* is one thing, *Home Assistant read it* is a reload, and *the automation exists* is a state in Core — and only the third is what you meant by pressing the button. A `mode:` Core does not recognise, a trigger from an integration that has not loaded, a read-only `/config`: each leaves a file on disk, a reload that returns fine, and no automation. Any of the three failing puts the file back, reloads again, and answers with the sentence — the proposal is exactly where it was, with no memory line and no settled entry.
- **Undo reverses all three effects, or says which one it could not.** Five minutes on the toast: the automation removed, Home Assistant reloaded, the proposal back on the list under its own id, and the queued memory line dropped. A trial that was still running when you accepted it comes back as a *proposal* rather than as a trial whose week has since passed, because "try it for a week" is a promise about the next seven days. If the file cannot be put back it says so rather than claiming a success — the automation is still running.
- **Four refusals, each a sentence rather than a guess.** An automation touching a **protected entity** (asked here as well as in the MCP server, because a YAML file the panel writes never passes through that chokepoint — and refused outright when it targets an area or a device, since expanding one needs registries this does not have). A `configuration.yaml` with no `automation: !include automations.yaml` line, where appending would be a change that silently does nothing — the refusal names the line it looked for. An `automations.yaml` that is not a list of automations. And a duplicate `id` or name.
- **The change announces itself**, as a change you asked for rather than as a problem brAIn found, and sent rather than held for quiet hours — it answers a press made seconds ago. The settled entry keeps the automation's id and entity id, because "accepted" and "accepted, and here is what it became" are different claims and only the second can be checked six months later.
- **Diagnostics report trials apart from their results.** "3 trialling, 0 with a result" is the exact shape of the failure this release fixes, and it is unreadable from a single count.

</Changes>
<Changes type="fixed">

- **A protected entity is dropped at the miner as well as at the writer.** The writer has to refuse one, being the last gate before `/config` — but a card offering something brAIn will not do is a wasted no.

</Changes>
</Release>

<Release version="1.43.1" date="September 4, 2026">

<Changes type="fixed">

- **The morning brief never saw the health verdict.** It awaited a plain function, so every call raised, the surrounding `try` logged it at *info* and carried on with an empty verdict — and the "brAIn itself is degraded" reason could never be the thing that made a brief worth sending.
- **`every day` was granted at the weekday hour to a house that sleeps in at weekends.** The two halves of the week each held up on their own, but nothing asked whether they held up at the *same* time: fifteen weekday presses at 07:00 hid six weekend ones at 10:00 completely, and the answer came back as `every day at 07:00` with a spread of zero. The halves have to agree on the hour now, and when they do not the answer is the narrower true claim rather than nothing at all.
- **Fix it had no Home Assistant.** Card and fix runs are deliberately run from the add-on's own home directory so their transcripts stay out of the Chats rail — and they inherited neither `.mcp.json` nor the project's permissions, so "Fix it" answered, accurately, that it had no working Home Assistant connection. The project is lent by flag now, and only the fixer gets the settings file, because the analyst's allow-list is asserted from both ends.
- **A finding's title was sliced at 200 characters, mid-word.** The model wrote the whole argument into the title, the store kept the first 200 characters and threw the rest away, so the card read *"something you int"* and the sentence saying what to do was gone. An over-long title is now cut at its last sentence end and the remainder leads the detail.
- **"Claude account connected 🎉" fired on every return to the tab.** The sign-in poll toasted whenever the server said `done`, which it does for as long as the credential lives. The toast is for *arriving* at done now, and a return to the tab no longer polls a finished sign-in at all.
- **Discuss opens its own conversation** instead of appending the garage lights to a half-finished question about the heating.
- **Switching the chat to the classic terminal froze the panel** for up to ten seconds — the handoff ran a blocking subprocess directly on the event loop, stalling every request, every stream and the terminal bridge. It runs on a thread.

</Changes>
</Release>

<Release version="1.43.0" date="September 4, 2026">

**Signing in, from the panel.** brAIn could sign you in **once** and after that had nothing to say about it: the sign-in screen was gated on a credential existing, and a credential exists long after it has stopped working — so the exact state that needed the screen was the one state with nothing to press. `/api/auth/logout` had existed since the first release and nothing in the UI ever called it.

<Changes type="added">

- **⚙ Settings → Claude account**, the first section of the dialog, because everything else in there is a preference and this is what decides whether the add-on works at all. It names the credential in use, **which of the three stores it came from**, when it was saved and the verdict of the last real check — then **Sign in again**, **Check it now** and **Sign out**.
- **All three credential stores, always.** A surface that can see only its own file answers "signed in and shared" with "not signed in", which is exactly what `ha login --status` did to somebody who had signed in through the panel perfectly well.
- **Sharing a login is a button now**, not something only `ha login` could do. It stays off unless you turn it on, and the dialog says why: `/config` rides in Home Assistant backups, which are unencrypted unless you opted in.
- **`brain login`**, the same command as `ha login` — the split is brAIn's faculties versus Home Assistant operations, and a credential is neither, so both spellings are things people type. `ha login --share` publishes a login you already have, and `--status` reports all three stores with the CLI's expiry read.
- **Check it now** re-earns the verdict on demand. It was otherwise only ever re-earned on a six-hour ageing — right for an unattended poll, useless to somebody who has just fixed their login in the terminal and is looking at a chip that still says it failed.

</Changes>
<Changes type="fixed">

- **`ha login` with no terminal hung forever instead of refusing.** `claude setup-token` prints a link and then blocks reading a code from stdin; with nothing attached it simply sat there, and the last thing printed was "Starting the Claude OAuth token flow…", which is indistinguishable from working. It refuses immediately now, naming the routes that do work without a terminal.
- **The auth chip is a control.** It renders only for trouble, and trouble is exactly when there is something to press — it was a `<span>` with no handler, unreachable from a keyboard.
- **Signing out while a login was shared left you signed in**, because the shared file is read two branches below the panel's own. The dialog now says a shared copy exists and offers to take it with you.
- **Three places told people to run `ha-share-login`**, which has never been a command — it is a filename; only `brain` and `ha` are on PATH.
- **Claude Code's own session token is refused for sharing, in a sentence.** It is short-lived and refreshed in place, so a copy works for a few hours and then breaks every add-on reading it, silently — and it is the store most likely to be the only one present, which is exactly when somebody reaches for the button.

</Changes>
</Release>

<Release version="1.42.0" date="September 4, 2026">

**Trying a change without committing the house to it.** Everything ranked above the forecasts on brAIn's capability map stood on one thing it could not do.

<Changes type="added">

- **[The shadow runner](/brain/replay/) — what an automation *would* have done.** It evaluates triggers and conditions against the recorded past and reports when the automation would have fired and what it would have done, calling no service and touching nothing: *"over the last 30 days this would have fired 26 times; on 4 a condition would have blocked it."*
- **The scope is four trigger kinds and the refusal is the feature.** Time, state, numeric-state and template are what the recorder can reconstruct; anything else is refused **whole**, naming the kind — never trimmed to the replayable part, because "this would have fired twice" about an automation whose webhook fires forty times a day is a confident wrong number that reads exactly like a right one.
- **[Proposals](/brain/proposals/) — the fifth kind of knowledge, with its own store and its own tab.** A list of things you might want sitting beside a list of things that are broken makes both worse. The lifecycle is `proposed → trialling → accepted | declined`, and the key is the **change** rather than the sentence, so a miner that rewords its explanation is still offering what you declined.
- **The habit miner — what you already do by hand.** Six separate *days* rather than six presses, a share of the days it could have happened on, a time rather than a stretch of evening, it has to still be happening, and nothing may already do it. `every day` has to be earned twice, once on each half of the week, because a habit on ten weekdays and one Sunday would otherwise build a trigger that fires on two mornings nobody wanted.
- **Diagnostics carry the miner and the store.** A tab with nothing on it reads the same whether the miner found no habit or the ledger has been empty since March.

</Changes>
<Changes type="fixed">

- **The image did not ship Jinja, and only a comment said it did.** The template branch carried a pragma claiming the image shipped `jinja2` and the Dockerfile installed no such package, so **every template trigger refused on every real install** while three tests passed on machines that happened to have it from somewhere else. A comment cannot fail.
- **The history query was built by pasting entity ids into a URL, in three places**, past a docstring that already said not to and said why. On the replay path the ids arrive in an HTTP body, so an id carrying `&` becomes a second parameter — a partial SSRF; everywhere else the same character corrupts the call quietly, which is the failure nobody would ever have traced.

<Release version="1.5.1" date="July 29, 2026">

<Release version="1.5.0" date="July 29, 2026">

**No default cards — it learns your home first.**

brAIn used to ship nine cards (Overview, Energy, Climate, Lighting, Security, Presence, Media, Device Health, Automations), all enabled from the moment you installed it. They generated before brAIn knew anything about the house, so they said generic things about a home it had never looked at — and cost tokens doing it, on every schedule, forever.

<Changes type="changed">

- **A fresh install now has no cards at all.** The first run studies the home — naming, occupancy, energy, climate, device reliability — and only then proposes cards grounded in what it actually found, each with a one-line reason citing the evidence. You pick which to keep. Nothing generates, and the scheduler stays idle, until you do.
- **There is no canned fallback.** If the home is too sparse to learn from, brAIn says what's missing and stops. Generic cards about a house it can't read would be noise on every run, and would teach you to ignore the dashboard.
- **The flow is resumable** — close the panel mid-study and come back — and re-running it never re-studies a topic it already covered, because a study session is expensive.

</Changes>
</Release>

<Release version="1.4.1" date="July 29, 2026">
<Changes type="fixed">

- **Answering a guess from an insight card never settled it.** When hypotheses replaced open questions in 1.3.0, the Memory tab was updated but the card renderer and its endpoints were not. Cards still showed a free-text "Answer" box — asking for an essay where the answer is yes or no — and the handler wrote to the old question ledger instead of the queue. The card looked answered while the guess stayed **open in Memory until it expired a fortnight later**. Cards now show the same two-tap ✓/✗, and settle the queue by resolving the claim's text (a card carries the text, not the id).

<Release version="1.4.0" date="July 29, 2026">

**A single, compact bar** — and the guess you click is the guess that gets settled.

<Changes type="fixed">

- **Clicking ✓ on the second or third pending guess settled the first one.** Hypotheses used the current epoch second as their id, and a study session proposes several claims inside the same second — so they collided, and settling matched whichever came first in the file. Ids are now unique per entry. (`knowledge_store` had guarded against exactly this; the hypothesis queue didn't inherit it.)

</Changes>
<Changes type="changed">

- **One 48px bar instead of two stacked bars plus a row of labelled buttons.** Roughly 110px of fixed furniture sat above every view, which on the **terminal** — where each pixel is a line of output — cost real content. The bar now carries the mark, the tabs, status and actions.
- **Monochrome line icons**, inline SVG inheriting `currentColor`, so they follow tab state rather than competing with it. Azure is the only colour in the chrome and it marks only what is active.
- Toolbar actions are **icon-only** — the labels were noise beside four tabs. On narrow screens the tab labels drop and the icons stay, so all four still fit.
- **The Memory tab shows a count** when guesses are waiting. A guess nobody sees is a guess that expires unanswered.

</Changes>
</Release>

<Release version="1.3.0" date="July 29, 2026">

**Guesses instead of questions.** Insight runs no longer ask open-ended questions. They state what they **believe**, phrased for a yes/no: *"The garage fridge is meant to run 24/7 — right?"*

<Changes type="changed">

- **Two taps settle it.** **Yes** files it as a plain memory line; **No** records a dead end that is never revisited. The cap is enforced in code, not just asked for in the prompt — a model that ignores the budget still cannot grow the queue. Three open at once, 14-day expiry, and a claim already proposed is never proposed again in any wording.
- **Turn limits were too tight, and failed badly.** A turn cap does not degrade — it **truncates**. A run that hits one stops mid-thought and produces nothing parseable, so the tokens are spent and the result is lost. That made a tight cap the most expensive setting in the add-on. Study sessions: 14 turns → **60**, timeout 10 → **30 minutes**, and `study_max_turns: 0` now removes the cap entirely. `brain ask`: 8 → **30**. Automation tasks: 10 → **30**. Voice: 5 → **8**, deliberately still modest, because latency *is* the product for voice.
- Hitting the limit is now **reported as** hitting the limit, rather than as unparseable output — blaming the model for a limit we imposed sends you looking in the wrong place. Study prompts also tell the model to land its result if it senses it is running short, so a long session degrades to partial instead of losing everything.

</Changes>
<Changes type="added">

- **Logbook events.** Every new fact fires `brain_learned`, so *"brAIn learned: the hallway sensor drops offline around 2am"* appears in your home's timeline next to lights and doors.
- **`sensor.brain_facts_learned`** and **`sensor.brain_last_learned`**.
- **`binary_sensor.brain_waiting_on_you`** — on when a guess needs an answer, with the text in `pending`. This exists to be automated: a guess sitting in a panel nobody has open expires unanswered, but pushed to a phone it costs one tap.
- **`brain.study`** service — with a topic, or without one to study whatever has gone stalest. Returns immediately; results arrive in memory, not in a response.
- **`/learn`** and **`/memory`** slash commands in the terminal, where you can watch a session work and correct it mid-flight.

</Changes>
</Release>

<Release version="1.1.1" date="July 29, 2026">
<Changes type="fixed">

<Release version="1.0.1" date="July 29, 2026">

<Release version="1.0.0" date="July 28, 2026">

First release. brAIn replaces **[BRUH Terminal](/brain/archive/bruh-terminal-changelog/)** and **[BRUH Insights](/brain/archive/bruh-insights-changelog/)**, which are now deprecated. It is a clean install — there is no migration from either add-on.

<Changes type="added">

- **The terminal and the insights dashboard now share a process.** They were two containers, which meant authenticating Claude twice, two Claude clients, two settings stores, and two writers racing on one memory file. Now it's one of each.
- **One ingress panel** serves everything. The panel owns port 8099 and reverse-proxies `/terminal/` through to ttyd (HTTP + WebSocket), so the terminal is a tab rather than a second sidebar entry. Port 7681 is still published for direct access. `enable_terminal` / `enable_insights` turn either face off.
- **An edit journal, replacing git backups.** A `PreToolUse` hook snapshots a file's prior contents before Claude writes to it, and **`brain undo`** lists those edits in plain English and restores one. It records only what Claude touched, lives under `/data` so it never pollutes the config directory, and prunes on `edit_journal_days` (default 14).

</Changes>
<Changes type="changed">

- **The assist worker pool moved to port 8098**, since 8099 now belongs to the panel. Nothing hardcodes it — the integration reads the port from the endpoint file the pool publishes.
- **Integration domain is `brain`**: services are `brain.send_prompt`, `brain.run_task`, and the rest, including all 56 Power Tools. Shared state moved from `/config/.bruh_claude/` to **`/config/.brain/`**, environment variables use the `BRAIN_` prefix, and the conversation agent appears as **brAIn** in Settings → Voice Assistants.
- **`assist_learning` is now just `learning`** — it governs everything brAIn learns, not only the voice channel.
- **Fourteen `ha-*` scripts collapse into two dispatchers**, split by what they act on: **`brain`** for its own faculties (`memory`, `learn`, `ask`, `undo`, `doctor`) and **`ha`** for Home Assistant operations (`log`, `reload`, `entity`, `service`, `addon`, `notify`, `share`, `check`, `context`). If a pre-existing `ha` command is ever found on `PATH`, brAIn installs its own as `hass` instead rather than shadowing it.

</Changes>
<Changes type="removed">

- **Git auto-backup** — `auto_backup`, `backup_interval_minutes`, the 30-minute commit watcher, and the `.gitignore` management that came with them. Versioning the whole of `/config` inside `/config` duplicated what a real Home Assistant backup already does, and the repo it grew was then swept into those backups. Existing `/config/.git` directories are left strictly alone; delete yours if you don't want it. The `git` binary is still installed — it's useful in a terminal.

</Changes>
