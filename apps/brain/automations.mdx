Ways to put Claude to work without opening the panel.

## `brain.ask` — answers an automation can branch on

A question in, and the answer back as **data** — not a sentence your automation has to
parse. Hand it the shape you want as a JSON schema; Claude looks the answer up (read-only
by default) and returns an object that has already been checked against that shape.

```yaml
automation:
  - alias: "Warn when any room is cold at bedtime"
    trigger:
      - platform: time
        at: "22:00:00"
    action:
      - action: brain.ask
        data:
          question: Which rooms are below 18 °C right now, and how far below?
          schema:
            type: object
            properties:
              rooms:
                type: array
                items:
                  type: object
                  properties:
                    name: { type: string }
                    degrees_below: { type: number }
                  required: [name, degrees_below]
            required: [rooms]
        response_variable: cold
      - if: "{{ cold.data.rooms | length > 0 }}"
        then:
          - action: notify.mobile_app_phone
            data:
              message: >-
                Cold tonight: {{ cold.data.rooms | map(attribute='name') | join(', ') }}
```

`response` always holds the answer as text; `data` holds the object when you gave a
`schema`. `tools` is `read_only` (the default — a question isn't a change), `house` (it may
control devices) or `full` (shell and files too).

## `brain.run_task` — background jobs

Runs Claude as a background task from any automation or script — error-log digests, config audits, morning summaries — with an optional notification when it's done.

```yaml
automation:
  - alias: "Nightly error digest"
    trigger:
      - platform: time
        at: "23:30:00"
    action:
      - service: brain.run_task
        data:
          prompt: >-
            Check the Home Assistant error log for today. Summarize real
            problems (ignore benign warnings) and suggest fixes.
          notify: true
          notify_entity: notify.mobile_app_phone
          timeout: 300
```

Tasks run with a generous budget (nobody is waiting on a background job, so they may take as many steps as they need, within `timeout`) and full MCP access — including [Power Tools](/brain/power-tools/), so a task can *fix* what it finds, not just report it. Responses are also returned as service response data for use in the same automation — and like `brain.ask`, `brain.run_task` takes a `schema` and returns `data`.

`notify: true` sends a notification when the task completes, and `notify_entity` picks the notify service that gets it — omit it for a persistent notification in the HA UI. (Before 1.26.0, `notify: true` silently did nothing: the listener posted a key the notify schema rejects, so every completion notification was a silent 400.) A `model` field on both `brain.run_task` and `brain.send_prompt` overrides the model per call (`default`, `sonnet`, `opus`, `haiku`), so a nightly digest can run on Haiku while everything else follows the add-on setting.

## `brain.send_prompt` — one-shot Q&A

A synchronous question → answer call, ideal inside scripts that need Claude's answer immediately:

```yaml
- service: brain.send_prompt
  data:
    prompt: "In one sentence: is anything in the house open or unlocked right now?"
  response_variable: claude
- service: notify.mobile_app_phone
  data:
    message: "{{ claude.response }}"
```

## Insight jobs

Scheduled reports rendered to **sensors** — the dashboard-native sibling of the panel's [insight cards](/brain/insights/).

Create them from the integration: **Settings → Devices & Services → brAIn → Add service → Insight job**. Pick a shipped template — daily briefing, anomaly watch, battery & maintenance, camera check — or write a custom prompt. Custom prompts can embed HA templating (`{{ states('sensor.outdoor_temp') }}`), rendered just before each run.

- **Scheduling**: an interval, a daily time (HH:MM), both, or manual-only. Every job also gets a **Run now** button, and `brain.run_insight` triggers by name from automations.
- **Reading it**: the report lives in the sensor's attributes — `preview`, full `markdown`, and ready-to-paste `card_yaml`. After the first successful run you get a notification containing the dashboard card.
- **Continuity**: each run receives the home [memory](/brain/memory/) plus the previous report, so recurring insights note what *changed* instead of rediscovering the house.
- **Events**: `brain_insight_complete` fires after every run with `name`, `entity_id`, `success`, and a `preview` — ideal for TTS announcements.

```yaml
type: markdown
title: Morning Briefing
content: >-
  {{ state_attr('sensor.morning_briefing_insight', 'markdown')
     or 'No insight yet — run brain.run_insight.' }}
```

Jobs or [insight cards](/brain/insights/)? Jobs produce glanceable markdown on dashboards and TTS-able events; cards produce interactive visual analysis you click into. Both read the same memory, so most homes use jobs for tiles and briefings, and cards for deep dives.

## Findings, cases and changes in automations

The [findings](/brain/findings/) list lives in the add-on's `/data`, which Home Assistant
can't see — so the add-on mirrors it to `/config/.brain/findings_state.json` on every change,
and the integration builds these on it:

| Entity or event | What it's for |
| --- | --- |
| **`sensor.brain_findings_open_findings`** | The open count, with the severity split and the texts as attributes — enough to put what's actually broken on a lock screen. |
| **`todo.brain_system_brain`** | brAIn's to-do list, in Home Assistant's To-do app. `brain.add_todo` adds to it. |
| **`brain_case`** event | Something new needs a decision — a problem, a guess or a suggestion. Carries the case, including its answer buttons. |
| **`brain_case_ended`** event | A case left the list — answered, cleared by its check, or moved to the to-do list. |
| **`brain_change`** event | brAIn changed something in your house (a fix you approved was applied). |
| **`brain_finding`** event | The older per-finding event, still fired beside `brain_case`. |
| **Repairs** | Every finding waiting on you, with its answers, under **Settings → System → Repairs**. |

```yaml title="Tell the kitchen speaker when brAIn fixes something"
automation:
  - alias: "Announce brAIn fixes"
    trigger:
      - platform: event
        event_type: brain_change
    action:
      - action: tts.speak
        target: { entity_id: tts.home_assistant_cloud }
        data:
          media_player_entity_id: media_player.kitchen
          message: "brAIn fixed something: {{ trigger.event.data.title }}"
```

**Zero YAML**: set the `findings_notify_service` option to any `notify.*` service and
findings reach your phone with no automation at all — critical ones pushed at once and asked
about again, others held through quiet hours, and each notification carrying its answer
buttons plus **Reply**. `findings_notify_min_severity` (default `critical`) decides what may
ring.

`brain.check` runs the house checks now instead of waiting for the next scheduled pass.

**`brain_learned`** fires when a fact is filed into [memory](/brain/memory/). The other
direction is `brain.add_memory`, which queues a fact from an automation; its optional
`source` field records where the fact came from.

## Power Tools from automations

Every [Power Tools](/brain/power-tools/) service is a normal HA service — automations can call them directly, no Claude in the loop:

```yaml
# Flag it in Repairs when the washer finishes but nobody empties it
- service: brain.create_repair_issue
  data:
    title: "Washing machine done"
    description: "Cycle finished over 2 hours ago and the door hasn't opened."
    severity: warning
    issue_id: washer_forgotten
```
