Before you enable an automation, brAIn replays it against your recorded history and tells
you when it would have fired and what it would have done. It calls no service and changes
nothing.

> *Over the last 30 days this would have fired **26 times**. On 4 of those a condition
> would have blocked it, so it would have run **22 times**. It would have called
> `light.turn_off` on `light.kitchen`.*

The answer takes seconds.

## Where you use it

| Where | What it answers |
| --- | --- |
| A proposal on **Needs you** | Each proposal shows its replay before you accept it. [Proposals →](/brain/proposals/) |
| An automation you already have | What it has been doing, including automations you did not write |
| A [condition suggestion](/brain/intents/) | The evidence for adding the condition |
| A [one-week trial](/brain/proposals/#the-three-verdicts) | The same replay over the week you are living through, graded against the presses you made |
| `POST /api/replay` | The same answer for an automation config you send |

## What can be replayed

| Trigger | Replayed | Notes |
| --- | --- | --- |
| `time` | Yes | Arithmetic |
| `state` | Yes | `for:` is honoured. See [below](#how-triggers-are-counted) |
| `numeric_state` | Yes | Counted as a crossing |
| `template` | Yes | With [limits](#template-triggers) |
| The new editor's triggers, such as "When a light turns on" | Yes, the common ones | See [below](#the-new-editors-triggers) |
| `webhook`, `mqtt`, `event` | No | The recorder does not keep what they fire on |
| `sun`, a brightness threshold | No | In the recorder, but brAIn cannot replay them yet |

:::caution[One unsupported trigger refuses the whole replay]
brAIn never trims an automation to the triggers it can replay. A count that leaves out a
webhook firing forty times a day would read like a right number. The refusal names the
trigger and says which kind of no it is:

*A `webhook` trigger cannot be replayed — the recorder does not keep what it fires on, so
brAIn would be guessing at how often it fired.*
:::

### The new editor's triggers

Since Home Assistant 2026.7 the automation editor writes purpose-specific triggers with
the device under `target:`. brAIn replays these as the state changes Home Assistant fires
them on, along with the matching conditions:

| Domain | Triggers |
| --- | --- |
| Lights, switches, fans | Turned on, turned off |
| Motion and occupancy | `motion.detected`, `motion.cleared`, `occupancy.detected`, `occupancy.cleared` |
| Locks | `lock.locked`, `lock.unlocked`, `lock.jammed`, `lock.opened` |
| Doors and windows | `door.opened`, `door.closed`, `window.opened`, `window.closed` |
| Covers | Opened and closed, for awnings, blinds, curtains, shades and shutters |
| Climate | `climate.turned_on`, `climate.turned_off`, `climate.started_heating`, `climate.started_cooling`, `climate.started_drying` |
| Media players | `media_player.turned_on`, `media_player.turned_off`, `media_player.started_playing`, `media_player.stopped_playing`, `media_player.paused_playing` |
| Alarm panels | Armed (any mode, away, home, night, vacation), disarmed, triggered |

A target that is a **whole area, floor, label or device** is refused. Which entities those
held at the time is something brAIn would have to guess.

### Template triggers

A template is replayed only when brAIn can rebuild everything it reads:

- **Every entity it names needs recorded history.** A template that reads a sensor with no
  history is refused. A blank would read as `unknown`, then as `false`.
- **Only these helpers are allowed:** `states`, `is_state`, `state_attr`, `is_state_attr`,
  `has_value`, `now`, `utcnow`, `as_timestamp`, `float`, `int`, `round`, `abs`, `min` and
  `max`. Anything else, such as a custom filter, `expand` or a loop over all `states`, is
  refused by name.

## How triggers are counted

- **`for:` needs the whole stretch.** A state trigger with `for: 00:05:00` counts only where
  the entity stayed that way for five minutes. A three-minute door blip does not count. A
  light dimmed during the hold still counts, because only an attribute changed.
- **`numeric_state` counts crossings.** It fires when a value moves into the range, as Home
  Assistant does, and not for every sample inside it.
- **Area and device targets in actions are reported as written.** brAIn does not expand
  them into entities, because the registry may have been different then.

## Limits

| Limit | What happens |
| --- | --- |
| **30 days** of history at most | The recorder keeps 10 days by default. A replay cannot reach past what your recorder kept |
| **500 firings** at most | brAIn says the trigger watches something that changes constantly, and suggests a `to:` or a `for:` |
| **25 entities** per replay | History is fetched for at most 25 entities |
| A condition it cannot evaluate | The replay is refused. brAIn does not assume the condition passed |

## What a replay does not tell you

A replay is not a simulation of your house. It reports when the triggers and conditions
would have matched what was recorded. It does not model what would have happened
differently had the automation been running.

If a proposal would have turned a light off at 23:05, the replay says so. It does not
replay the rest of the evening with that light off. A
[trial](/brain/proposals/#the-three-verdicts) adds evidence a replay cannot: it is graded
against the presses you made during the week.
